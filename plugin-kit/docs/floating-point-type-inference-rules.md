# 浮点类型向目标端推演规则

## 1. 目的与范围

本文定义源字段已推演为 `TapFloat` 或 `TapDouble` 时，如何从目标数据源的类型规格中选择目标类型。规则只约束这两种源 TapType 的向下游推演；其他 TapType 继续使用既有推演流程。

推演分为两个彼此独立的阶段：

1. **源端归类**：由源数据源规格把字段归类为 `TapFloat` 或 `TapDouble`。目标端选择不得反向改变源端归类。
2. **目标端选择**：依据源 TapType，按本规则限定的目标类型档位选择。不得把不同档位的候选放进同一个全局评分池。

例如，SQL Server 的 `real` 应先由源规格归类为 `TapFloat`；之后才应用 `TapFloat` 的目标选择规则。目标类型的名字或目标端评分不能把这个源字段改判为 `TapDouble`。

## 2. 术语

**目标映射项**：目标数据源类型规格中的一个类型表达式及其 Tap 映射配置。

**目标档位**：映射项根据其声明能力可解析到的 Tap 家族。固定映射由 `to` 声明；动态映射必须依据其明确声明的能力范围判定。例如，系数映射须检查 `coefficient` 中是否声明了 `TapFloat` 或 `TapDouble` 范围，不能仅因映射类名称含有 `Float`，或源字段是 `TapFloat`，就假定它属于某一档。

**档位存在**：目标规格中至少有一个非 `queryOnly` 映射项声明支持该档位。档位存在与该映射项本次能否成功生成具体表达式是两件事：前者决定是否允许降档，后者决定本档内能否选出结果。

**可用候选**：映射项根据源 TapType 生成了具体目标表达式，表达式没有未展开的变量或可选片段，并且该表达式重新按目标规格解析后仍属于预期档位。

## 3. 强制档位顺序

### 3.1 源类型为 `TapFloat`

依次处理以下档位：

1. `TapFloat`
2. `TapDouble`
3. `TapNumber`

对每个档位，先收集该档的全部目标映射项，再在本档候选中选最合适项。只有当前档位**不存在任何声明支持该档的目标映射项**时，才允许进入下一档。

因此，只要目标规格中存在一个 `TapFloat` 映射项，最终结果就必须来自 `TapFloat` 档。即使该档本次没有可用候选，也不得改选 `TapDouble` 或 `TapNumber`；应报告本档推演失败，且不得输出未展开模板。

### 3.2 源类型为 `TapDouble`

依次处理以下档位：

1. `TapDouble`
2. `TapNumber`

`TapDouble` 源字段永远不得降到 `TapFloat`。只要目标规格存在 `TapDouble` 档映射项，最终结果就必须来自该档；本档无法生成可用候选时应报告失败，不得继续选择 `TapNumber`。

### 3.3 档位隔离

不同档位之间不比较 `matchingScore`、`priority` 或其他评分。档位顺序先于所有候选评分：高优先级档位只要存在，就锁定选择范围。评分只能用于同一档位内部的候选排序。

## 4. 档位内的候选选择

每个档位内必须对所有映射项进行评估，不能用以 `priority` 为唯一键的容器覆盖同优先级候选。

候选排序只在**同一档位**内进行，顺序如下：

1. `matchingScore` 越高越优。
2. 分数相同则较小的 `priority` 越优。
3. `priority` 未配置或同值时，按目标 `datatypes` 中类型定义的先后顺序选择。`priority` 是可选项，不得因其缺失而拒绝推演。

同档同分同优先级时，类型定义顺序就是确定的决胜规则；不得再用表达式字典序或运行时 map 的分组遍历顺序替代。

## 5. 表达式生成与校验

每个候选必须分别完成以下校验，全部通过后才能参与本档排序：

1. 映射项能根据源 TapType 生成目标表达式。
2. 结果非空，且结果状态成功。
3. 结果是完整、具体的目标表达式，不得残留 `$precision`、`$scale` 等变量，也不得残留未处理的可选片段标记。
4. 使用目标数据源的表达式匹配规格重新解析该结果。
5. 重新解析所得 TapType 必须属于当前档。特别地，`TapFloat` 和 `TapDouble` 虽然在 Java 类型层级上属于 `TapNumber`，但不能因此被当作 `TapNumber` 档候选。

不能通过校验的候选必须从本档候选排序中排除。排除候选不会改变档位是否存在，也就不会授权降到下一档。

## 6. SQL Server 到 MySQL 示例

假设源字段 `real` 已由 SQL Server 源规格推演为 `TapFloat`，目标 MySQL 规格中同时定义了：

- 一个或多个映射到 `TapFloat` 的类型表达式，包括 `float` 及带参数的 float 表达式；
- 映射到 `TapDouble` 的 `double` 类型；
- 映射到 `TapNumber` 的数值类型。

目标选择必须先只考虑所有 `TapFloat` 映射项。`double` 不能因为评分更高而越过 `TapFloat` 档。参数化表达式若仍输出为 `float($precision,$scale)`，不是可用候选；该结果不得进入字段推演结果。最终应从可用的 `TapFloat` 候选中选出最合适项。

若目标规格没有任何 `TapFloat` 能力声明，才考虑 `TapDouble`；若也没有 `TapDouble`，才考虑 `TapNumber`。同理，`TapDouble` 源字段从 `TapDouble` 开始，缺少该档后才考虑 `TapNumber`。

## 7. 不在本文中擅自决定的事项

以下行为需要产品/业务规则确认后才能编码：

1. **高档存在但无可用候选时的错误呈现**：规则要求不得降档或输出模板；具体是抛出推演错误、返回字段级诊断，还是由调用方处理，须明确接口行为。
2. **三个数值档均不存在时的既有兜底行为**：是否继续走自定义 codec、全局评分或字符串兜底。本文的强制层级只覆盖 `TapFloat`/`TapDouble` 目标映射档，未授权修改这些末端兼容行为。
3. **目标映射可写性**：除 `queryOnly` 外，`cannotWrite` 等标志是否影响“档位存在”及候选可用性，需与当前建表/写入语义统一。

在这些事项确认前，不应通过代码实现选择一个看似合理但未经确认的答案。

## 8. 验收条件

- `TapFloat` 只会按 `TapFloat → TapDouble → TapNumber` 的档位顺序选择；`TapDouble` 只会按 `TapDouble → TapNumber` 的顺序选择。
- 只要更高档存在声明映射，低档就不能因评分、优先级、候选渲染失败或遍历顺序而胜出。
- 返回的目标表达式可被目标规格重新解析为预期档位，不包含未展开模板。
- priority 未配置时，同档候选按 `datatypes` 定义顺序稳定决胜。
- 非 `TapFloat`/`TapDouble` 源类型的推演结果保持原有行为。
